
Коротко:

- **Consent** — согласие пользователя.
- **Context flow** — сценарий/поток действий с учётом контекста: где пользователь находится, что он делает, какие права уже дал или не дал.
- **Toggles** — переключатели: включить/выключить функцию.

Разберу по-русски и на примере вашего приложения «Движ».

## 1. Что такое consent?

**Consent** — это информированное согласие пользователя.

В контексте приложения и магазинов это значит: прежде чем приложение начнёт что-то собирать или запрашивать разрешение, пользователь должен понять:

- что приложение делает;
- какие данные будут храниться;
- где они хранятся;
- передаются ли куда-то;
- можно ли отказаться;
- можно ли потом удалить;
- подтверждает ли пользователь возраст, если это важно.

### Пример в вашем приложении

При первом запуске показываем экран:

```text
Приложение «Движ» работает офлайн.

Данные о тренировках хранятся только на этом устройстве.
Приложение не отправляет данные на сервер.
Приложение не использует рекламу и аналитику.
Для подсчёта шагов нужен доступ к датчику движения.

[ ] Я ознакомился с политикой конфиденциальности
[ ] Мне исполнилось 14 лет, либо я использую приложение с согласия законного представителя
[ ] Я понимаю, что данные не передаются автоматически

[ Продолжить ]
```

Кнопка «Продолжить» должна быть неактивна, пока пользователь не поставил нужные галочки.

### Зачем это нужно

Это нужно для:

- 152-ФЗ, если данные можно отнести к персональным;
- Google Play Data Safety;
- RuStore;
- нормальной этики к пользователю;
- снижения риска жалоб.

### Важно

Consent должен быть:

- **до** запроса разрешения;
- **до** сбора данных;
- **понятным**, не юридическим туманом;
- **добровольным**;
- **отзываемым**: пользователь должен иметь возможность удалить данные или отключить функцию.

## 2. Что такое context flow?

**Context flow** — это не один термин из стандарта, а инженерно-продуктовое понятие. Обычно имеется в виду:

> поток сценариев пользователя с учётом контекста: состояние приложения, разрешения, экран, история действий, ошибки, настройки.

То есть вы проектируете не просто «кнопка → экран», а понимаете: пользователь сейчас впервые запустил приложение? уже дал разрешение? отключил уведомления? начал тренировку? вышел в фон? нажал «удалить данные»?

### Примеры context flow в «Движ»

#### Сценарий 1: Первый запуск

```text
Открыл приложение
→ увидел privacy consent
→ подтвердил возраст
→ нажал «Продолжить»
→ попал на главный экран
→ ещё не запрашивался датчик движения
```

#### Сценарий 2: Пользователь хочет начать тренировку

```text
Главный экран
→ выбрал «Ходьба»
→ нажал «Начать»
→ приложение проверяет: consent есть?
→ приложение проверяет: запись включена?
→ приложение проверяет: разрешение на датчики есть?
→ если разрешения нет — показывает объяснение
→ пользователь разрешает
→ запускается таймер и счётчик шагов
→ показывается уведомление, если уведомления включены
```

#### Сценарий 3: Пользователь отказал в разрешении

```text
Нажал «Начать»
→ система показала запрос разрешения
→ пользователь нажал «Не разрешать»
→ приложение не падает
→ показывает текст:
   «Для подсчёта шагов нужен доступ к датчикам движения.
    Включите разрешение в настройках системы.»
→ кнопка «Начать» остаётся неактивной или снова предлагает открыть настройки
```

#### Сценарий 4: Пользователь свернул приложение

```text
Идёт тренировка
→ пользователь вышел в фон
→ если уведомления включены, видно ongoing notification
→ если Android убил процесс, после возврата состояние может восстановиться или корректно завершиться
→ нельзя терять данные молча без объяснения
```

#### Сценарий 5: Пользователь удаляет данные

```text
Настройки
→ «Удалить все данные»
→ confirmation dialog: «Действие необратимо»
→ удаляется SQLite
→ очищаются SharedPreferences
→ приложение возвращается к состоянию первого запуска или показывает экран согласия заново
```

### Почему context flow важен

Он помогает ответить на вопросы:

- когда запрашивать разрешение;
- когда показывать объяснение;
- что делать при отказе;
- что делать при ошибке;
- где пользователь может удалить данные;
- какие состояния приложения возможны;
- как не сломать UX и compliance одновременно.

### Простыми словами

**Consent** — «пользователь согласился».  
**Context flow** — «что происходит дальше, в каком контексте и при каких условиях».

## 3. Что такое toggles?

**Toggle** — это переключатель: вкл/выкл.

В настройках приложения это могут быть такие тумблеры:

```text
Разрешить запись активности       [ON / OFF]
Показывать уведомления            [ON / OFF]
Тёмная тема                       [ON / OFF]
Считать шаги только при движении  [ON / OFF]
```

### Какие toggles нужны в вашей версии

Для Google Play-safe версии я бы оставил минимум:

#### 1. Master toggle записи

```text
Разрешить запись активности
```

Если **OFF**:

- кнопка «Начать» неактивна;
- датчики не запускаются;
- шаги не считаются;
- уведомления не создаются;
- пользователь видит пояснение: «Запись отключена в настройках».

Зачем:

- пользователь может полностью выключить функцию;
- снижает тревожность;
- удобно для тестирования;
- соответствует принципу минимизации обработки.

#### 2. Toggle уведомлений

```text
Показывать уведомление во время записи
```

Если **OFF**:

- не запрашиваем `POST_NOTIFICATIONS`;
- не показываем уведомление;
- запись всё равно может идти, если пользователь не закрывает приложение.

Если **ON**:

- показываем тихое ongoing notification;
- без звука;
- без вибрации;
- без рекламы;
- исчезает после остановки.

#### 3. Toggle темы

```text
Тема: системная / светлая / тёмная
```

Это не критично для compliance, но полезно для UX и экономии батареи на AMOLED.

#### 4. Опционально: toggle точности/экономии

Например:

```text
Экономный режим датчика
```

Можно переключать частоту опроса акселерометра:

- 20 Гц — экономия батареи;
- 50 Гц — чуть точнее, но больше расход.

Для MVP я бы не делал это сложной настройкой, лучше задать разумное значение по умолчанию.

## 4. Как это связано между собой

Пример правильной связки:

```text
Consent
↓
Пользователь согласился с политикой и возрастом
↓
Context flow
↓
Приложение понимает: можно ли запрашивать разрешение, включена ли запись, есть ли история
↓
Toggles
↓
Пользователь может выключить запись и уведомления
↓
Data controls
↓
Пользователь может очистить историю или удалить все данные
```

## 5. Что это значит для вашего приложения конкретно

### Consent

Нужен экран первого запуска:

- политика конфиденциальности;
- подтверждение возраста;
- понимание, что приложение офлайн;
- согласие до запроса датчиков.

### Context flow

Нужно описать состояния:

1. Первый запуск.
2. Согласие получено.
3. Запись включена.
4. Запись выключена.
5. Разрешение на датчики есть.
6. Разрешение на датчики нет.
7. Уведомления включены.
8. Уведомления выключены.
9. Идёт тренировка.
10. Тренировка завершена.
11. История очищена.
12. Все данные удалены.

### Toggles

Минимально:

```text
Разрешить запись [ON/OFF]
Показывать уведомления [ON/OFF]
Тема [системная/светлая/тёмная]
```

## 6. Простая аналогия

Представьте приложение как комнату:

- **Consent** — пользователь подписал входной лист: «Я знаю, куда захожу и что здесь происходит».
- **Context flow** — маршрутизатор: куда идти, если свет включён, если дверь закрыта, если пользователь передумал.
- **Toggles** — выключатели света и сигнализации: можно включить, можно выключить.

## Итог

- **Consent** — согласие пользователя до сбора/обработки данных.
- **Context flow** — понятный сценарий поведения приложения в зависимости от состояния, разрешений и действий пользователя.
- **Toggles** — переключатели функций: запись, уведомления, тема и т.д.

Для вашего «Движ» это означает:

> сначала спросить согласие, потом дать пользователю включать/выключать запись и уведомления, и всегда держать понятный путь к удалению данных.
